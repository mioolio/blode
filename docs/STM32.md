# STM32、Arm Compiler 与 ST-Link

STM32 使用独立的 ST-Link / SWD 调试连接。COM 串口用于串口监视，ST-Link 不必出现在 COM 列表。当前源码编译配置明确支持已识别的 `0x410` STM32F1 中容量 Cortex-M3 目标；其他芯片拒绝源码编译，可在真实目标与容量已确认后使用外部生成的完整二进制验证路径。

## 连接与识别

1. 连接 ST-Link 的 SWDIO、SWCLK、GND，确认目标供电与电压匹配。
2. 使用自动检测选择明确候选，或选择 STM32 / ST-Link 及探针序列号。
3. 顶栏齿轮的“驱动”负责 Windows 驱动；“工具链”负责 ST-Link 命令行工具与 Arm Compiler 路径，二者分别检测。
4. 识别芯片并核对实际 ID、Flash 和 SRAM。多台调试器不默认选第一台，无法确认芯片或容量时保留诊断输出并拒绝继续。

发现串口、安装好驱动、识别到探针、成功连接目标是不同结果。仅发现 USB 接口不能证明当前固件适用于该 MCU。

## 两种构建输入

右键工程中的文件或目录选择编译入口，只写入 `be.build.entry`，不会立即编译。随后保存工程并执行构建：

- 有 entry：使用 Arm Compiler 6 的 armclang 编译 C/C++，armlink 链接，fromelf 输出二进制。entry 可为文件、目录或 `.`。
- 无 entry：保留根目录 `firmware.bin` 的现有二进制验证，不运行源码编译。

字段片段示例，不是完整工程描述符：

```json
{
  "toolchain": {
    "armCompilerDirectory": "",
    "stlinkDirectory": ""
  },
  "build": {
    "entry": "."
  }
}
```

工具链其他必需字段仍由正常工程配置保存；不要用以上片段覆盖整个 be。armCompilerDirectory 可指完整 Arm Compiler 目录或其 bin 目录；留空使用平台工具根目录中的 armclang 安装。stlinkDirectory 可指已有 st-info/st-flash 目录，留空使用托管工具或 PATH。

## 源码、启动与链接限制

单独一个 main.c 不保证构成可启动的 MCU 固件。源码工程需要适合目标的头文件/库、启动向量、架构选项、链接布局及初始化逻辑。

当前编译配置采用 Cortex-M3、Thumb、软件浮点，并为已识别的 0x410 STM32F1 中容量目标提供启动和 Arm scatter 模板。项目同时提供可识别的 Arm 汇编启动文件与一个 scatter 时优先使用项目配置；多份启动或 scatter 不能静默任选。

内置启动模板通过 AC6 标准 `__main` 完成 scatter 装载、RW/ZI 初始化和 C/C++ 运行库初始化，再进入应用；C++ 全局构造调用链已用实际 ELF 反汇编检查。默认 scatter 在 `0x20004c00..0x20005000` 保留 1 KiB 向下增长的栈，静态 RW/ZI 区不能侵入该范围。

GNU 启动汇编与 GNU .ld 不能当作 Arm scatter 直接传入 armlink。对已知目标，无法采用的启动/链接输入会给出提示并使用平台模板；未知芯片拒绝猜测 CPU 或内存。使用模板不意味着项目原有 GNU 链接脚本已被转换。工程依赖的时钟、引脚、中断和外设配置仍需由用户工程正确提供。

模板回退不保证 GNU 脚本的自定义 section、保留区域或绝对地址仍然相同。构建出现回退提示时，须检查 warning 与 firmware.map，确认实际布局符合固件要求；不能把编译成功当作原工程链接语义已完整保留。当前直接编译受支持输入，不执行任意项目构建脚本。

编译结果位于 `.blode/build/`：firmware.elf、firmware.map 和 firmware.bin。容量检查读取实际 ELF 的 Flash 装载范围和 SRAM 段，并计入链接器保留的栈；还会检查二进制的初始栈指针、Thumb 复位入口与物理范围。显示的 RAM 占用是静态数据与保留栈的合计，不是运行时峰值，也不通过源码长度估算资源。实际可烧录产物使用构建记录中的二进制，不把旧的根目录固件冒充此次编译结果。

本次 Arm Compiler 6.22 对用户工程副本的实际编译得到 Flash 使用 2136 字节、RAM 占用 1028 字节，其中静态数据 4 字节、链接器保留栈 1024 字节。数据来自生成的固件与 ELF/链接布局，只验证这份输入能够构建，不证明固件已在硬件上运行，也不能作为其他项目的容量估计。

## 固件烧录边界

先识别目标，再完成源码构建或二进制验证。完整固件必须为真实芯片生成，从 `0x08000000` 开始映射。烧录前复核芯片 ID、容量、输入与产物哈希；过期或改动的固件必须重新构建/验证。

当前只接受单一、offset=0、size≤flashSize 的 app 区，应用区按 1 KiB 对齐，可以从 Flash 尾部留出保留区。STM32 按页/扇区擦除，因此禁用 ESP 式任意分区编辑，不适用于自定义偏移、独立 bootloader 或需保留相邻页数据的模式。布局页通过 `layout` 能力从 `0x08000000` 起调整应用区，`partitions` 能力保持关闭。程序不自动解锁芯片、修改选项字节或发起整片擦除命令。

布局页可以添加数据区、系统区，并为区域设置名称和颜色；这些区域是保留区，不写入内容。应用区不填大小时默认使用探测到的物理容量。源码链接使用物理 Flash 以生成完整镜像，但编译结果会按应用区/保留区逐段检查：固件超出应用区或覆盖保留区时输出 WARNING，界面提示，烧录确认弹窗仍允许用户二次确认后继续。超过物理 Flash 或 RAM 越界仍拒绝构建。RAM 继续按 F1 中容量目标的固定 20 KiB 检查并保留 1 KiB 栈，不提供任意 RAM 分配。

ST-Link 报告的是芯片自述容量，克隆或改写过的芯片可能误报。布局页允许手动选择或输入容量，保存后写入 `flashSizeOverride`；再次识别芯片不会覆盖该值。手动容量只允许小于或等于探测值，超过探测容量仍拒绝烧录，避免写入不存在的地址。

确认目标和固件后才调用 st-flash，写入后由工具回读校验。驱动、识别、构建、烧录和应用运行应分别验证；编译器成功退出也不能替代真实硬件运行结果。

## 工具目录与许可

本机原 E 盘的 Arm Compiler 6.22 完整目录已迁入应用 `tools/armclang/`，保留 bin、include、lib、sw 与原始 license_terms，旧目录不再用于配置。项目不跟踪这些工具二进制。当前本机工具版本标识为 Keil MDK Community 非商业使用环境，使用和重新分发须遵循随工具保留的原许可。

平台源码目录可以复制并注册到匹配宿主，但不包含编译器；分享平台代码不等于取得编译器重分发许可或转授本机工具授权。

ST-Link 托管工具使用固定官方发行及 SHA-256 校验，开发位置为 `tools/stlink/`；Windows 签名驱动归档位于 `tools/STSW-LINK/`。详见 [工具链说明](TOOLCHAINS.md) 与 [平台包说明](../extensions/boards/stm32/README.md)。

## 自动化

`devices.scan` 扫描平台候选，`probes.list` 列出调试器，`device.probe` 识别明确目标。构建使用同一 CoreApi；烧录请求仍需用户授权和 `confirm=true`，设置编译入口本身不会触发构建或设备写入。
